## 1. 削除済みデータの復活防止

**原因**：`applyOp` は「サーバー側が新しければ衝突」としか判定しておらず、削除済みの記録（data=NULL）に対しても、端末の `updatedAt` が新しければ put で上書き＝復活していた。書き込みも無条件の upsert だった。

**修正**（`apps/api/src/routes/sync.ts`）
- 削除済み（tombstone：ユーザー削除・期限削除・復元閲覧の終了）は**最優先**。baseVersion・updatedAt に関係なく put は適用せず、`conflict` + `serverDeleted: true` + `deleteReason` を返す。拒否は操作ログ（`put-refused`）に残す。削除の再送は版を増やさない。
- 書き込みを**条件付き更新**に変更（`WHERE version = 読んだ版 AND deleted = 0`／新規は `ON CONFLICT DO NOTHING`）。期限削除などが間に入って条件が外れたら読み直して判定し直す。3回続けば `retry`（端末は変更を捨てずに後で再送）。受領記録・操作ログは書き込みが実際に入ったときだけ残す。
- put は復元閲覧中の印 `restored_session_id` を変えない（閲覧中に編集しても恒久的に戻ったことにしない）。**記録を戻せるのは `/restore` API だけ**。
- 端末（`apps/web/src/sync/engine.ts`）：`serverDeleted` を受けたら端末の記録も削除し、編集していた場合は「削除済みのデータへの変更は反映されませんでした」をお知らせに出す（期限削除なら「期間指定の復元」から戻せる旨も）。変更内容は端末の操作ログに残る。`retry` は未送信のまま残す。
- 契約（`packages/contracts`）：`PushResult` に `serverDeleted`・`deleteReason`・`retry` を追加。

**回帰テスト**：削除後に古い baseVersion・新しい updatedAt の put／版を最新に偽った put を拒否、オフライン端末が期限削除後に再接続しても復活しない（翌日のバックアップにも入らない）、復元閲覧の終了後も put で戻らず `/restore` なら戻る、期限削除と古い端末の送信を同時実行しても削除後を上書きしない（API）。端末側でオフライン編集が削除に負けてお知らせが出る（Web 単体）。

## 2. Google OAuth のログイン CSRF 対策

**原因**：state はサーバーで1回限り検証していたが、ログインを始めたブラウザとの結び付きがなかった。攻撃者が自分の同意で得た callback URL を被害者に開かせると、被害者のブラウザが攻撃者のアカウントでログインしてしまう。

**修正**（`apps/api/src/routes/auth.ts`、`migrations/0002_review_fixes.sql`）
- `/login` でブラウザ固有の乱数を HttpOnly・SameSite=Lax・path=/api/auth・10分の Cookie（`mt_login`）で渡し、`state.乱数` のハッシュを `oauth_states.browser_hash` に保存。
- `/callback` は state を**照合の成否にかかわらず消費**し、期限切れ・存在しない・Cookie なし・Cookie 不一致をすべて拒否（一定時間比較）。Cookie も1回で削除。
- ログイン成功時、このブラウザの以前のセッションを破棄して作り直す（セッション固定の防止）。
- ログアウトにも独自ヘッダー必須（他サイトからの強制ログアウト防止）。
- PKCE(S256)・ID トークンの JWKS 検証（aud/iss/exp）・HttpOnly セッション Cookie・リフレッシュトークンの暗号化は維持。

**回帰テスト**：攻撃者の callback URL を被害者のブラウザ（自分のセッションあり／別の印あり）で開いても被害者のセッションは変わらず攻撃者のユーザーも作られない、失敗した state は攻撃者自身も再利用不可、state の再利用・期限切れ・Cookie なしを拒否、同じブラウザで別アカウントにログインすると旧セッションは無効、ログアウトのヘッダー必須（API）。実ブラウザでも、ログインを始めていないブラウザで callback を開くとログインされないことを確認（サーバー連携 E2E）。

## 3. ローカルデータのアカウント別分離

**原因**：IndexedDB が1つだけで、ログイン中のアカウントと端末データの持ち主を区別していなかった。A のデータ・未送信キューが B のログインで B に送られる。

**修正**
- 保存領域をアカウントごとに分離（`apps/web/src/data/db.ts`）：`my-time@<ユーザーID>`＝そのアカウントの領域、`my-time`＝ログインしていない間の領域（Phase 1 からのデータもここ）。表示中の領域は端末に記憶し、切り替えは再読み込みで行う（画面・同期・ライブクエリがすべて新しい領域で始まる）。
- 同期エンジン（`engine.ts`）は**表示中の領域の持ち主＝ログイン中のアカウント**のときだけ送受信する。さらに送受信に `x-mytime-account` を付け、サーバー（`requireUser`）も一致を確認して違えば 409（送らずに確認し直す）。
- 別アカウントの領域を表示中にログインが変わった → 何も送らず、ログイン中のアカウントの領域へ切り替え。前のアカウントの未送信は端末に残り、そのアカウントで入り直すと送信（件数を案内）。
- ログインしていない間のデータがある状態でログイン → **件数（タスク・予定など）と移行先のメールアドレスを示す確認画面**（`AccountChoice.tsx`）。選ぶまで送信しない。「移して同期」は移行先に新規作成として入れてから元を空にする（同じIDは移行先を優先・途中で止まっても二重にならない）。「移さない」は端末に残し、ログアウトすると表示される。データがなければ確認なしで切り替え。
- ログアウト → ログインしていない領域に戻る（アカウントのデータ・未送信は端末に残す）。セッション切れ（401）では切り替えず、同じアカウントで入り直せば続きから送る。
- 新しい領域は外観などの設定を引き継ぎ、初回セットアップを出さない。「その他」に「表示中のデータ」を表示。

**回帰テスト**：A の領域で B にログインしても送受信せず切り替え・A の未送信が残る、409 で確認し直す、ログイン前データの確認画面・移行・移行先での送信、「移さない」、データなしなら確認なし、ログアウト→再ログインで続きから送信、401 で切り替えない（Web 単体）、サーバーのアカウント不一致拒否（API）、実ブラウザでログイン前データの確認→移行→ログアウト→別アカウント B（A のデータが出ない・サーバーにも入らない）→A に戻すとデータが戻る（サーバー連携 E2E、Chromium/WebKit）。

## 4. 30日削除の仕様統一

**修正**（`packages/domain/src/retention.ts`）：起点は次の順で1つ。
1. 試験日時が設定されたテスト対策 … 試験日時から30日
2. 確認日時のある確認タスク … 確認日時から30日
3. 作業日時（予定の開始・終了）がある … 終了日時から30日
4. それ以外（**提出期限だけの課題・試験日のないテスト対策も含む**）… 作成日から30日

「保留（hold）」状態は廃止。いずれも起点より後に実績の終了があれば遅い方を採る（早く消さない）。繰り返し・日付またぎの特則・バックアップ失敗時の保留は変更なし。

**テスト**：上記4種＋作業日時のある課題・試験日なしのテスト対策・実績終了が遅い場合（ドメイン）、提出期限のみの課題が作成から90日で削除・10日では残る（API）。

## 5. バックアップの安全性

- **日次バックアップの中身を拡充**（スナップショット版 3）：現役の記録に加え、**アプリ設定**（端末から同期するようにした）・**操作ログ**・**削除済みの印**を含める。版 2 のアーカイブも引き続き復元できる。

- **復元試験**（`POST /api/backups/:id/drill`、画面は「バックアップ管理」の各行の「復元試験」）：Drive から読み戻し → ハッシュ・件数を検証 → 復元したら得られる記録を作り、現在のデータと1件ずつ比べる（読み取りのみ）。アーカイブは削除直前の版と比べる。
- **期限削除の切り替え** `RETENTION_MODE`：未設定・不明な値＝**off（停止）**／dry-run＝件数を記録して知らせるだけ／on＝実行。`wrangler.toml` の本番既定は `off`、手動公開ワークフローは GitHub Variables の `RETENTION_MODE`（未設定なら off）を渡す。画面に現在の状態を表示。

**テスト**：日次バックアップに設定・操作ログ・削除の印が入り、復元試験で全件一致・バックアップ後の変更は差分として検出、アーカイブから戻した内容が削除直前と完全一致、off/未設定/不明値/dry-run/on の挙動、`wrangler.toml` の既定が off、**古い端末の再接続 × 同期の衝突 × 期限削除の同時実行**（新しい方が残る・期限切れは復活しない・その後のバックアップは現在と完全一致）。

## セキュリティ・データ保護上の残存リスク（隠さない）
1. **本物の Google / Drive / Cloudflare では未検証**。OAuth・Drive・cron はすべて模擬 Google とローカル Worker で確認した。本番では手順書の「復元試験」と dry-run を経てから期限削除を有効にする運用が前提。
2. **復元閲覧中に編集した記録**は、閲覧を終了すると編集ごと通常画面から外れる（Drive のアーカイブには削除前の内容が残る。閲覧中の編集内容自体はサーバーの操作ログと端末の操作ログに残る）。「戻したデータを恒久的に残す」操作は未実装（専用 API として追加する場合は要件の確認が必要）。
3. **端末内データの暗号化はしていない**。アカウントごとに分けたが、同じ端末・同じブラウザのプロファイルを使う人は IndexedDB を見られる（ブラウザの一般的な制約）。共用端末ではログアウトしても前のアカウントのデータが端末に残る（未送信の保護を優先したため。消去する操作は本人の明示的な許可が必要なので未実装）。
4. **ログイン前データの移行は「同じIDは移行先優先」**。初期カレンダー（一般・授業・アルバイト）を両方で編集していた場合、ログイン前の編集は移されない（件数表示には含めていない）。
5. 操作ログはバックアップのたびに全件を含めるため、長期間の利用でバックアップのサイズが増える（数年分でも数MB程度の見込み。必要なら Phase 3 で期間を区切る）。
6. 同時実行の判定（条件付き更新）は D1 の単一書き込みの原子性に依存している。D1 のトランザクション分離は SQLite の直列実行のため問題ない想定だが、本番の負荷では未検証。
7. Google の「テスト中」アプリは約7日でリフレッシュトークンが失効する場合がある。失効時はバックアップと期限削除が止まり「!」で知らせる（データは消さない）。
