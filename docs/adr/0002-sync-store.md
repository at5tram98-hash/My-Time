# ADR 0002：同期の保存形式とデータ保護ゲート

- 状態：採用（Phase 2）
- 日付：2026-10-31

## 背景
端末（Dexie / IndexedDB）を正とするオフライン優先のアプリで、複数端末の同期、毎日22時の Drive バックアップ、
30日後の期限削除、期間指定復元を、データを失わずに実現する必要がある。

## 決定
1. **サーバーは汎用の `records` 表**（user_id, entity, id, version, data, deleted, delete_reason, server_seq, restored_session_id）。
   エンティティごとの表を作らず、検証は共有の Zod スキーマ（`packages/contracts`）で行う。項目追加でマイグレーション不要。
2. **送信は opId による冪等**。`sync_receipts` に結果を保存し、再送には同じ結果を返す。
3. **削除（tombstone）は最優先**（2026-11-01 レビュー対応）。ユーザー削除・期限削除・復元閲覧の終了で `deleted = 1` になった記録には、
   baseVersion や `updatedAt` に関係なく put を適用しない（`conflict` + `serverDeleted: true` を返し、端末も削除する）。記録の復活は `/restore` API だけが行う。
   put は復元閲覧中の印（`restored_session_id`）を変えないので、閲覧中に編集しても恒久的に戻ったことにはならない。
4. **競合は version（楽観ロック）**。baseVersion が古い場合は `updatedAt` が新しい方を採用し、古い側には `conflict` と最新の記録を返す。
   書き込みは「読んだ版のまま・未削除」のときだけ成功する条件付き更新。期限削除などと同時に走って条件が外れたら読み直して判定し直し、
   3回続けば `retry`（端末は変更を残して後で再送）。
5. **受信（pull）は server_seq のカーソル**。未送信の変更がある記録は受信で上書きしない。
6. **期限削除はゲート付き**（`RETENTION_MODE`：未設定は off、dry-run は件数の記録だけ、on で実行）：その日の日次バックアップが「Drive へ保存 → ダウンロード → ハッシュ・件数一致」で検証済みのときだけ、
   対象をアーカイブとして別保存・検証してから、`version = ?` 条件付きで論理削除（reason=purge）する。`purge_ledger` に記録。
   繰り返し予定は親を消さず、該当回に `archived` 例外を付ける。
7. **復元は restoration_session 単位**。閲覧中の記録には `restored_session_id` を付けて期限処理の対象外にし、
   「閲覧を終了」で reason=restore-end として外す。Drive のファイルは消さない。
8. **端末の保存領域はアカウントごと**（IndexedDB `my-time@<userId>`。`my-time` はログインしていない間の領域）。
   送受信は表示中の領域の持ち主＝ログイン中のアカウントのときだけ行い、`x-mytime-account` ヘッダーでサーバーも照合する（違えば 409）。
   ログインしていない間のデータは、件数と移行先を示して本人が選んだときだけ移す。
9. **日次バックアップの中身**（スナップショット版 3）：現役の記録＋アプリ設定＋操作ログ＋削除済みの印。
   「復元試験」（`POST /backups/:id/drill`）で、Drive から読み戻した内容から復元した記録が現在のデータと1件ずつ一致するかを確認できる（読み取りのみ）。
10. Workers は UTC で動くため、すべての入口で `applyUserZone`（Asia/Tokyo）を呼び、日付判定をユーザーの時間帯で行う。

## 結果
- API テスト（workerd + 実 D1）とサーバー連携 E2E（ローカル Worker + 模擬 Google、Chromium/WebKit）で、
  「バックアップ失敗日は削除しない」「読み戻し不一致は成功扱いしない」「同日再実行は冪等」「復元中は再削除しない」「閲覧終了後も Drive に残る」を確認済み。
- レビュー対応後の回帰テスト：オフライン端末の再接続で期限削除済みが復活しない／削除後の古い put・版を偽った put を拒否／
  期限削除と古い端末の送信の同時実行／ログイン CSRF／アカウント不一致の送受信拒否／ログイン前データの移行確認／ログアウト・再ログイン・切替。
- 汎用表のため SQL での集計は不便（分析は端末側で計算するので問題なし）。
